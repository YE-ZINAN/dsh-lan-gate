## 三、机制分析（含代码位置）

1. **网关给每个远程客户端各开一条独立的上游 WS**：
   `lan-gate.mjs:485 server.on('upgrade', …)` → `lan-gate.mjs:504 net.connect(UPSTREAM_PORT, UPSTREAM_HOST, …)`，
   双向 pipe（`514/515`），一个方向出错就 `kill('上游 ' + e.message)`（`523`）。
   → 所以 **N 个远程客户端 = N 条到 `/api/remote.mux` 的上游连接**。
2. **所有远程客户端共用同一个 `DSH_COOKIE`**：`upstreamHeaders(clientReq.headers, { cookie: DSH_COOKIE })`（`135` / `505`）。
   → 上游无法从 cookie 区分不同客户端。
3. **日志事实**：多客户端并发时上游连接被 reset（`01:38:05 上游 write ECONNRESET`），随后客户端成对断开（`01:38:30` ×2）。

**待本插件会话验证的假设（按优先级）**

| # | 假设 | 怎么验 |
|---|---|---|
| H1 | 上游 `/api/remote.mux` 只允许**一个**活跃连接（或按会话去重）→ 第二个客户端接入把前一个挤掉 | 单客户端长连 30 分钟 vs 两个客户端并发，比较断开率 |
| H2 | 共用同一个 cookie 让上游把两条连接视为**同一会话的重复**，从而 reset | 给每个设备签发不同 cookie / 在请求里带上设备标识，看是否还断 |
| H3 | 网关侧**半开处理**不足：只 destroy 上游、没同时通知/关闭客户端，也没有重连退避 | 断开时两侧的关闭是否成对；客户端是否有重连兜底 |

**症状链（与用户描述逐条对应）**：远程客户端 WS 断开 → 客户端失去 workspace/session 的**实时投影** →
(a) 分组退化成 `group.ungrouped`（界面文案「未定义工作区」）；
(b) 提交的选择拿不到回执 → 界面回滚成"未选择"；
(c) 新建会话的请求/列表刷新失败。
宿主侧数据是全的（2.4），所以**不是数据损坏，是同步断了**。

## 四、复现与验证步骤（建议）

1. **只开原生 DSH 窗口**（直连 `127.0.0.1:19387`），做同样的工作区/新建会话操作 → 预期正常。这是最快的定性。
2. 同时开**原生窗口 + 一个网关窗口** → 看 `run.log` 是否出现 `WS 断开`。
3. 同时开**两个网关客户端**（本机 Chrome + 手机）→ 看 ECONNRESET 是否稳定复现。
4. **单客户端**长连 30 分钟 → 看是否也断（区分"多客户端互踢"与"单连接本身不稳"）。

日志位置：`dsh-lan-gate/run.log`（标准输出被重定向到这里；`run.err.log` 今天为 0 字节）。

## 五、已排除项（供本条会话不再重复排查）

- **皮肤插件 `dsh-skin-qq2005` 不是原因**：本现象是**连接级**的（上游 socket 被 reset），皮肤只作用于渲染层，且不碰任何 WebSocket / 网络代码。
  皮肤此前确实有两个**真** bug（浮窗 `z-index` 先是 `2147483000`、后是 `900`，压住宿主的菜单 `101` 与模态框 `1000`），
  **已分别于 0.19.2 / 0.19.3 修复并发布**（判据与宿主层级表见该插件 README §4.14），但那属于"点击被吞掉"，**不会导致上游连接断开**。
- 磁盘空间、localStorage 配额、渲染进程崩溃、Windows 事件日志：均查过，无异常。

## 六、影响与处置建议

- **影响**：任何"经网关的窗口"在**依赖实时状态同步**的操作（工作区分组、把会话挂到工作区、新建会话）上都可能失灵；宿主数据不会丢，但用户看到的是失败。
- **短期**：工作区/新建会话请**在原生窗口**里做；同一时间只保留**一个**远程客户端。
- **长期**：按第三节 H1/H2/H3 的方向修（连接去重 / 每设备独立凭据 / 半开与重连处理）。

## 七、验证结论（dsh-lan-gate 会话，2026-10-08）：**网关不是原因，H1/H2 均不成立**

验证方式：**宿主源码取证**（从 `D:\dsh\HARNESS\resources\app.asar` 抽出 `@deepseek-ai/dsh-api-gateway` 的 TS 源码）
+ **对照实验**（真 `ws` 8.21.0 客户端，经网关与直连上游各跑一遍）。所有读数来自工具回执。

### 7.1 源码证据（决定性）

| 事实 | 出处 | 对假设的影响 |
|---|---|---|
| mux 服务端持有的是 **`connections = new Set<Promise<void>>()`**，逐条 socket 独立登记，无单连接限制 | `dsh-api-gateway/src/stream-server.ts:45` | **H1 证伪** |
| `/api/remote.mux` 的准入是 `admit(req)`，而它 **恒返回进程级单例 `this.operator`**；该 peer 只在 **Connection 插件拆解时** dispose | `dsh-client-connection/lib/index.js:591`、`:569-570` | **H2 证伪** |
| `bindPeer()` 把 disposer 挂在**共享的 operator ctx** 上，socket 结束时只 `release()` 注销**自己那一条** | `stream-server.ts:410-420`、`:83-86` | 一条连接结束**不会**关掉另一条 |
| 心跳：**每 2 秒 ping**，`MAX_MISSED_HEARTBEATS = 2` → 约 4~6 秒收不到 pong 即 `socket.terminate()`（发 RST） | `src/index.ts:137`、`stream-server.ts:40,107-123` | 真实的失败模式是**心跳超时**，不是互相踢。桌面 profile 未覆盖该配置，用默认 2000ms |

### 7.2 实测证据（真 ws 客户端）

| 实验 | 结果 |
|---|---|
| **单条连接经网关，60s** | **存活**；ping 收 30 次（正好 2s 一次）；`open` 后立即收到 `{"type":"ready","clientId":...}` |
| **两条并发经网关，90s** | **两条都存活**（ping 49/48）；各自拿到**不同的 `clientId`**；**收到同一批事件**（广播给所有消费者） |
| 直连上游 `127.0.0.1:19387`（绕过网关） | 与经网关**行为一致** |

⇒ 多客户端并发本身完全正常。第三节日志里"两个客户端同时升级、随后同时断开"的形态，
**不能推出互相踢**——同时升级恰恰说明它们是被**同一个外部原因**同时触发的（例如同时重载/PWA 安装）。

### 7.3 那为什么日志看起来像"被 reset"？——网关的日志口径有偏

`lan-gate.mjs` 的 WS 处理里：

```js
upstreamSocket.on('error', (e) => kill('上游 ' + e.message));
clientSocket.on('error',  (e) => kill('客户端 ' + e.message));
clientSocket.on('close',  ()    => kill());          // ← 无参数，不打印
```

- **正常关闭（客户端发 FIN、关标签页、重载）走 `close` → 静默**；
- **只有异常关闭（RST）才打印**。

于是日志里**只剩** `WS 断开: 客户端 read ECONNRESET`，看起来像"总被 reset"，
而**正常的重载/关闭一条都不显示**。这正是本档第三节得出错误归因的直接诱因。

**待验证的推论**：01:37:51 / 01:38:30 / 01:49:21 等断开，紧邻其前的
`01:37:01 图标请求: icon-512 ← 100.101.102.103`、`01:37:40 图标请求 ← 100.101.102.104`
——**正是两台设备先后"添加到主屏幕"**。PWA 安装会触发页面重载，重载必然断 WS。

### 7.4 一处更正：本方验证过程中自身踩的坑（记录备查）

我最初手写了一个极简 WS 探针，得到"连接在 ~5 秒被干净关闭、一个 ping 都没收到"的读数，
一度据此怀疑是 Node HTTP 的 `keepAliveTimeout=5000`。**该读数是手写探针的缺陷造成的伪影**，
换成成熟库 `ws@8.21.0` 后同一路径 **60 秒稳活、ping 正常**。
→ **教训：验证 WS 行为不要手写帧解析；读数异常先换成熟实现复现一遍再下结论。**

### 7.5 结论与建议

1. **H1、H2 不成立**，不建议按它们改代码。
2. ~~症状与「实时投影断掉后客户端没有正确重订阅」一致~~ —— **该推论已作废，见 §7.6**。
   真因是**皮肤层级 + 客户端插件代码未重载**，与 mux 断连无关。第三节那条「症状链」是
   **看起来合理、但事实上错的**因果链——这正是本档最值得记住的一点。
3. **确实值得改的只有一处（H3 相关，且与本次症状无关）**：网关的 WS 关闭日志分不清"正常关闭"与"异常复位"，
   且缺少 `upstreamSocket.on('close')`。把两侧的关闭都记下来（含 code/reason），
   才不会让下一次排障继续被日志误导。

### 7.6 结案（2026-10-08 当日，用户确认）

**重启 DSH 宿主后症状消失。本档结案。**

| 项 | 结论 |
|---|---|
| 根因 | **皮肤浮层 z-index 盖住宿主工作区菜单**（详见 `45d8a0ed`）。**与网关、与 `remote.mux` 无关。** |
| 为什么"修了还犯" | 修复代码（皮肤 0.19.3 / `Z = 90`）**09:28 就已落盘**，但**正在运行的桌面窗口仍跑着旧代码**；用户当时未重启宿主。 |
| 修复动作 | 重启 DSH 宿主。 |

**可复用规则：改了 DSH 客户端插件（皮肤 / 客户端按钮等）的代码后，必须重启 DSH 宿主。**

> ⚠️ 浏览器硬刷新是否足够**未单独验证**——本次实测只到「重启有效」，不要简化成「刷新就行」。

> ⚠️ **不要再按第三节 H1/H2 的方向改网关**（连接去重 / 每设备独立 cookie）。
> 那两条已被源码与实验双重证伪（§7.1、§7.2）。

**本档留下的方法论教训**：`.ps1`/日志这类"取证材料"本身可能是误导源——
本次日志只记异常关闭、不记正常关闭，于是所有人都往"被动 reset"上想。
**排查前先确认取证口径是否对称。**
